# 2026.242.1445 — feat: ship the consumer-side frame probe

## Summary

Ships `/usr/local/bin/cstream-frame-probe` — a **consumer-side** probe that pulls a frame back
through the negotiated WebRTC track and writes it to a caller-given path.

It asserts something neither existing probe structurally can:

| probe | reads | can it fail on a transport defect? |
|---|---|---|
| `stream-probe` | the tap on the **producer's own** pipeline | **no** — proves frames are produced, says nothing about any leaving the process |
| `wl: screenshot` | the **compositor** | **no** — never touches the encoder or the wire |
| `cstream-frame-probe` | what a **real consumer decodes** | **yes** — fails on a broken encoder, negotiation, or transport |

That gap is not hypothetical. It is exactly what let a missing `webrtcbin` hide
(`opencharly/pod-cstream#7`): `webrtcsink` failed to build its session pipeline with a **WARN**, no
offer was ever sent, and **every producer-side check passed** while not one byte reached a consumer.
So the probe checks for that element first and says so by name, rather than timing out with a
generic "no frames".

**Two behaviours taken from measurement, not assumption:**

- `connect-to-first-producer` defaults to **false**. Without it a consumer connects to signalling and
  waits forever for a `peer-id` nobody supplies — no error, no frame, a timeout indistinguishable
  from a dead stream.
- The probe copies the **second-newest** frame. `multifilesink` is still writing the newest, so
  taking it can capture a truncated JPEG that fails a decode-based gate for a reason that has
  nothing to do with the stream.

The wait loop is **bounded and exits as soon as a frame lands** — it is a bound on a real condition,
not a sleep.

Nothing else changes behaviour.

Run with this branch overridden in, so the probe is installed by the candy and invoked by charly.

$ CHARLY_REPO_OVERRIDE='github.com/opencharly/pod-cstream=<this branch>' \

That scratch check runs `/usr/local/bin/cstream-frame-probe` and asserts
`stdout: contains: FRAME-OK` — a string the probe prints **only after a frame has actually arrived
and been copied** — so the PASS is evidence of received bytes, not merely of a process exiting 0.
Both legs moved from **60 steps / 56 passed** to **61 / 57**, and that one extra step is the scratch
check exercising this probe.

### 3. The mechanism, measured independently

Before `gst-plugins-bad` landed, the same consumer pipeline this probe runs received **0 frames**;
after, **1683** (55,988,362 bytes). That is what the probe is built to distinguish, and it is why
its first assertion is the presence of `webrtcbin`.

## What this does NOT do

It does **not** yet offer `cstream: frame`. The verb method lands separately in `plugin-cstream`,
which will call this probe over the executor and write the pulled frame to the step's `artifact:`
path so `artifact_min_bytes` / `artifact_not_uniform` can gate the **content**. Shipping the probe
first keeps each half gated on its own: this PR proves the probe retrieves a frame; the verb PR
proves the frame reaches a host artifact and is non-uniform.
