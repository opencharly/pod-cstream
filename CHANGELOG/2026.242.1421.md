# 2026.242.1421 — fix: install gst-plugins-bad -- webrtcsink is inert without webrtcbin

## Summary

The cstream stack negotiated a WebRTC session end to end — producer registered, consumer
registered, `startSession` sent, `started a session` logged — and then carried **no media**, with no
ICE or DTLS error anywhere to point at. This installs the missing package that causes it, and adds
the check that would have caught it.

**Root cause, read off the producer's own log rather than inferred:**

```
SessionPipelineError { session_id: "e8e3ce21-…", peer_id: "96d1c33b-…",
                       details: "Failed to make element webrtcbin" }
```

`webrtcsink` and `webrtcsrc` come from `gst-plugin-rswebrtc` and were present — but they construct a
**`webrtcbin` per session, internally**, and that element ships in `gst-plugins-bad`, which was never
installed. Only `gst-plugins-bad-libs` was, pulled in as a transitive dependency, and it carries the
shared libraries rather than the plugin:

```
$ pacman -Qq gst-plugins-bad gst-plugins-bad-libs
error: package 'gst-plugins-bad' was not found
gst-plugins-bad-libs

$ ls /usr/lib/gstreamer-1.0/ | grep -iE 'webrtc|nice|rtp'
libgstnice.so
libgstrsrtp.so
libgstrswebrtc.so          <- the sink/src …but no libgstwebrtc.so, so no webrtcbin

$ gst-inspect-1.0 webrtcbin ; echo $?
1
```

**Why it was invisible.** The pipeline-construction failure is a **`WARN`**, not an error. So the
sink registered, the session started, the offer was never sent, and the consumer waited until it
timed out — indistinguishable from a dead stream. That is exactly why every earlier investigation
found "no ICE/DTLS error": there was no `webrtcbin` to perform ICE or DTLS at all.

## What else changes, and why it matters more than the package

`cstream-webrtcsink-registered` **passed throughout the entire outage.** It asserts that
`gst-inspect-1.0 webrtcsink` succeeds, and its comment reasons carefully about ABI skew — but it
checks the wrong element. `webrtcsink` builds a `webrtcbin` per consumer at session time, so its own
registration says nothing about whether it can serve one.

This adds `cstream-webrtcbin-registered`, gating the element that was actually missing.
**Registration is not capability** — the same trap `cstream-streamer-graph` already covers on the
encoder side by asserting the VA encoder *opens* rather than merely appears in the registry. That
lesson existed in this bed; this check applies it to the transport.

## How tested

### 1. The defect and the fix, measured on a live pod

Both runs on the same running bed pod, one variable — the package:

```
BEFORE (gst-plugins-bad absent)
  gst-inspect-1.0 webrtcbin            -> ABSENT
  consumer frames received             -> 0
  producer "Failed to make element webrtcbin" -> 1

AFTER (gst-plugins-bad installed)
  gst-inspect-1.0 webrtcbin            -> PRESENT   (libgstwebrtc.so appears)
  consumer frames received             -> 1683      (55,988,362 bytes)
  producer "Failed to make element webrtcbin" -> 0
```

The consumer exit was `124` in both runs because it is a fixed `timeout 35` — in the AFTER run the
stream was still flowing when it was cut, which is what the 1683 frames record.

pod, so it establishes the mechanism; §2 is the evidence that the *shipped* change works.

`cstream-webrtcsink-registered`, its neighbour, passes on both.

## A finding this ruled out, recorded so it is not re-chased

A plausible competing hypothesis was tested and **refuted**: the pod has no global IPv6 (only `::1`
and link-local), while `webrtcsink`'s default `stun-server` is `stun://stun.l.google.com:19302`,
which resolves IPv6-first inside the container to an address that is `Network is unreachable`, with
the working IPv4 record right beside it. That predicted the symptom exactly and was still wrong:
`webrtcbin` was never created, so ICE never ran and the STUN server was never contacted.

It remains a real latent issue for when ICE *does* run — worth fixing separately by pinning
`stun-server` or disabling it for a loopback-only deployment — but it is not this defect, and this
PR does not claim it.
