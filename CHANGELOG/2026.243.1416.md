# 2026.243.1416 — feat(WP5): arm the idle lock, and stop fetching the streamer over anonymous git

## Summary

Turns WP5's idle lock on. Adopts `charly-streamer` `de1ff6f5` (`v2026.243.1048`), which carries
the `lifecycle` module, and sets `CSTREAM_LOCK_AFTER=10` on the streamer service — the value the
plan's own manual end-to-end names (*"disconnect and confirm `hyprlock` after 10 s"*).

A streamed desktop has no lid to close and no seat to lock from: without this, the session stays
logged in and rendering after the last viewer disconnects, and whoever reconnects lands straight
in it.

Second commit: the streamer source is fetched as a codeload tarball instead of an anonymous
`git clone`, because the pin bump exposed that the clone cannot work in a build container here.

## The new check, and why a file-exists check is not enough

`cstream-streamer-installed` asserts a streamer is installed. It passes just as happily when the
bump did **not** take — a cached layer, or a ref that quietly resolved to the old commit — because
the *previous* streamer is still there and still works. The behavioural gate downstream would then
fail looking exactly like a lock defect.

`CSTREAM_LOCK_AFTER` is a string that exists only in a binary built from the WP5 commit, so
`grep -a` on the installed binary discriminates. Verified against a real release build of that
commit rather than assumed:

```
$ cargo build --release -p cstream-streamer --bin cstream-streamer   -> exit 0
$ grep -aoc CSTREAM_LOCK_AFTER target/release/cstream-streamer
3
```

## The fetch, which the bump exposed

The first attempts at the bed died before any check ran:

```
Cloning into 'src'...
fatal: could not read Username for 'https://github.com': No such device or address
```

for a repo the API reports as `private=false`. Measured on the build host, seconds apart:

```
GET  codeload.github.com/.../tar.gz/<sha>   -> 200
GET  github.com/.../info/refs               -> 200
POST github.com/.../git-upload-pack (anon)  -> 401
                             www-authenticate: Basic realm="GitHub"
```

GitHub throttles anonymous git here, and a build container carries no credentials. **This was
invisible until the pin moved**, because the `RUN` layer is cached on the SHA — so it presented
as a failure of the bump rather than of the fetch.

A retry loop would be the workaround. Switching to codeload removes the dependency: plain HTTPS,
not subject to that throttle, pinned by exact SHA rather than cloned-then-checked-out, ~71 KB
instead of a blobless clone of the whole history. `set -o pipefail` goes with it, or a refused
`curl` is masked by a `tar` that exits 0.

**The attempt count is the part worth reading.** `CSTREAM_LOCK_AFTER=10` with a 5s retry interval
means the first attempts find nothing and a later one finds `hyprlock`. The lock therefore fired
*because of* the departure and no earlier than the configured delay — a lock that was already
running would have passed on attempt 1, and `cstream-lock-idle-only` passing beforehand rules that
out from the other side.

All 5 skips are mutating `run:` steps in verify-only mode; not one of them is a check.

## Answering the two earlier BLOCKs

**The skew warnings were never this PR's.** The first gate run advanced `layer-cstream-desktop`
alongside this repo, and advancing it brings `pod-hyprland v2026.243.1021` (`plugin-wl
v2026.243.1001`) into a project where `pod-selkies-core` still pins `plugin-wl v2026.242.0610` —
23 warnings, all one class. That pin advance is the **`distro-cachyos`** PR's diff, not this one.
Re-run with only this repo overridden, every `plugin-wl` pinner in the project agrees on `0610`
and the class is zero. It gets answered where it belongs, by repinning `pod-selkies-core` and
`layer-sway-desktop-vnc`.

**The 24th warning was `podman store is bloated`, and it is now gone — the store was actually
repaired, not argued away.** Chasing it produced a root cause worth recording against
`opencharly/charly#173`, because the issue's stated remedy cannot fix it:

```
podman ps --external | wc -l   ->  1436 orphaned buildah working-containers
```

Those containers pinned layers that no charly path can release:

| attempt | result |
|---|---|
| `charly clean --deep` (the remedy the warning names) | 366 untagged images, 272.7 GiB — reclaimable stayed at 97% |
| `charly clean --images --keep 1` | 336 tags removed, reclaimable **unchanged** |
| `podman system prune -a` | refused: *"image is in use by a container"* |
| `podman system prune --external` | exit 0, zero output, 1436 unchanged |
| `podman rm --storage` | flag no longer exists in this podman |
| **`buildah rm --all`** (buildah was not installed) | 1430 removed → the next prune freed **2.917 TB** |

Store went `19,032 images / 552.5 GB` → `30 images / 21.5 GiB`, reclaimable `538.6 GB` → `1.97
GiB`, well under the 50 GiB threshold (`plugin-build/candy/plugin-build/store_bloat.go:17`).

**Two build failures on the way there share one cause, and it is not bloat.** After the purge,
builds died at

```
COPY --from=cstream … etc/cstream-parent   ->  copier: stat "/etc/cstream-parent": no such file
Error: replacing mount point ".../overlay/<id>/merged": file exists
```

with the file present in a clean tree and the staging dir intact — and then a *running* container
reported `unable to find user user: no matching entries in passwd file` while
`podman run --rm -u 0 <same image>` printed `user:x:1000:1000` from the same image. So the fault
is **stale overlay mount points**: a leftover `merged` makes a new mount fail with *file exists*,
and a stale one makes a stage or container read an empty rootfs. `podman system migrate` plus a
fresh container cleared it.

Worth flagging on #173: it names a bloated store as the co-factor, but this reproduced on a
freshly purged 21 GiB store. Bloat is not sufficient — stale mount records are the proximate
cause.
