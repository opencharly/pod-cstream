# 2026.243.0814 — feat(WP6): adopt the audio-capable streamer, and guard the element it needs

## Summary

Adopts the audio-capable streamer and supplies the element it needs — **without enabling audio**,
because the path does not work in this pod yet.

Three changes to one file:

1. the pinned streamer advances to `f20647f9` — the WP6 audio branch (`charly-streamer#9`) plus its
   opt-in default (`charly-streamer#10`)
2. `gst-plugin-pipewire` is installed
3. `cstream-pipewiresrc-registered` guards it, at image level

## Why the package, and why a guard for it

`pod-pipewire` supplies the daemon, wireplumber and `pw-cli` — **not** the GStreamer element.
Without it the streamer aborted at startup:

```
Error: attaching the audio branch
  0: creating pipewiresrc — is gst-plugin-pipewire installed?
  1: Failed to find element factory with name 'pipewiresrc'
```

and because **the streamer IS the Wayland parent**, that took the entire session with it:

```
cstream-parent    FATAL    Exited too quickly
cstream-hyprland  RUNNING  uptime 0:00:06   (restart-looping, no parent display)
```

with the consumer-side frame probe then hanging **eleven minutes** on media that would never
arrive. The package is present on a dev host, which is exactly why no local test could have found
it — it is a host-vs-pod gap by construction.

The guard mirrors `cstream-webrtcbin-registered`, which exists because a missing element once
silently broke media. This is the same class and worse: absence here is *fatal*, not a WARN. Both
now fail at build rather than as a mystery hang in `check-live`.

## Audio stays OFF, deliberately

It is opt-in as of `charly-streamer#10`, and this PR does not opt in, because the path is not
reachable in this pod:

```
$ pw-cli ls Node    → cstream-speaker (Audio/Sink, id 30), cstream-mic (Audio/Source/Virtual, id 31)
$ gst-launch-1.0 pipewiresrc target-object=cstream-mic ! fakesink
  stream error: target not found        # identically for id 31, path=31, and for NO target at all
$ pw-cli ls Metadata → settings, schema-sm-settings      # no `default` object
```

So `pipewiresrc` resolves **no** target, including the default, and wireplumber has established no
defaults. Enabling audio would ship a feature that cannot work.

**A monitor-capture gate was written and then removed rather than shipped.** With audio off nothing
links to the monitor, so it would have asserted nothing while looking like coverage — the exact
"reports success having done nothing" shape this bed already has three checks guarding against. It
returns with the enablement, which is when it can discriminate.
