# 2026.242.2156 — feat(WP9b): ship the session target the compositor is scoped to

## Summary

Ships `cstream-session.target` — the lifetime `pod-hyprland`'s compositor unit is scoped to
(`pod-hyprland#6`) — by staging the unit file, and repins `pod-hyprland` onto that merged fix.

```yaml
- run: stage the cstream session target
  copy: etc/cstream-session.target
  to: /etc/systemd/system/cstream-session.target
  mode: "0644"
  run_as: root
```

### Why a raw unit and not a `service:` entry

A `.target` has **no cross-init analogue**. supervisord has no concept of one, so there is nothing
for the container rendering to produce — which is precisely why the systemd venue needed this and
why the pod venue never noticed its absence. `service:` carries what *both* renderings can express;
this is not one of them.

### Why it carries no `[Install]`

A target that pulled itself into `multi-user.target` would re-create, one level up, exactly the
defect `pod-hyprland#6` fixes: something started at boot with no session to attach to. It is pulled
in by a session starting, never by the machine booting. The bed asserts this — `systemctl
is-enabled` must not report `enabled`.

### Why NOT charly's `unit:` verb — measured, not assumed

`unit:` is the right seam in principle. `plugin-unit`'s own schema names
**`"cstream-session.target"`** as its worked example, and its WHY block condemns exactly the
hand-roll pattern this replaces. I migrated onto it, and **the bed caught that it does not work on
this venue.**

Measured on `check-cstream-vm`, each on a clean pacstrapped guest:

| `context:` | VM venue | container venue |
|---|---|---|
| *(none)* | `deploy-add` **exit 0**, unit **absent** | hard render error, self-diagnosing |
| `[runtime]` | `deploy-add` **exit 0**, unit **absent** | PASS (steps=13) |
| `[deploy]` | `deploy-add` **exit 0**, unit **absent** | — |

Confirmed by inspecting the live guest rather than trusting the deploy:

```
ls /etc/systemd/system/cstream-session.target  -> No such file or directory
systemctl show -p LoadState --value            -> not-found
```

**In every spelling the VM deploy reports success and installs nothing.**

**Mechanism — a hypothesis, labelled as such because I read it rather than executed it:**
`kit/walk.go`'s `Op` case routes a plugin act-verb to `RunHostStep`, commented *"a **builtin**
ProvisionActor … needs the **in-proc registry**"*. `plugin-unit` is **out-of-process**
(`plugin.source` + `providers: [verb:unit]` + `cmd/serve`), so it is not in that registry. The
build path uses a different seam — `EmitPluginOp` → `ex.InvokeProvider` — which *does* reach
out-of-process plugins. That asymmetry explains both columns: the container venue dispatched the
verb and produced a useful error; the VM venue silently did nothing.

So the container venue fails **loudly and self-diagnosing**, the machine venue fails **silently
behind a green deploy**, and only an assertion on the *outcome* distinguishes them.

### Why staging is not the hand-roll R4 forbids

The pattern R4 names is `write:` **+ `command: systemctl daemon-reload && systemctl enable`** — a
manual `systemctl` against a charly-managed resource. This step runs **no `systemctl` at all**, and
needs none: systemd lazy-loads a unit on first reference, which is exactly what the bed's
`LoadState` probe proves. `unit:` remains the correct destination; the candy comment records the
measurement so the next author does not re-derive it.

### Why the bed asserts `LoadState`, not `test -f`

A `.target` with a syntax error still exists on disk while systemd refuses to load it, and the
compositor's `WantedBy` would then resolve to nothing — a silent failure a file test passes.
`systemctl show -p LoadState` forces the load, so it also catches a unit written where the manager
does not read.

