# 2026.243.0310 — fix(R3): pod-cstream must not pin pod-hyprland — the layer owns that

## Summary

**`pod-cstream` must not pin `pod-hyprland`.** `layer-cstream-desktop` composes both pods and is the
only place that should. Removing the duplicate pin is the fix; the repin this PR originally proposed
was treating the symptom.

**The complete diff — two changed lines, verified against `git diff origin/main..HEAD`:**

```diff
@@ charly.yml:4 @@
-        version: 2026.243.0048
+        version: 2026.243.0245
@@ charly.yml:32 @@
-    - '@github.com/opencharly/pod-hyprland:v2026.242.2008'
+    # (a comment block explaining why nothing is pinned here)
```

1. **The candy's own `version:` `2026.243.0048` → `2026.243.0245`** — a CalVer stamp of the edit.
   `PickCandyVersion` is newest-wins, so an edited candy keeping its old stamp can be silently
   shadowed by the published copy.
2. **The `pod-hyprland` require is deleted**, replaced by a comment recording why, so it is not
   re-added.

## Why removal rather than a repin

`layer-cstream-desktop`'s own description states the rule:

> A metalayer's members are what it IS, so they are `candy:` entries … a metalayer that also
> installed things would give a consumer **two places to look for the same behaviour**, and the two
> members already own theirs.

Pinning `pod-hyprland` here was that second place, and it cost a permanent skew class: two pins on
one candy report `resolved to multiple versions` every time either side moves, and **no ordering of
cross-repo PRs can avoid it**, because they cannot change atomically.

**The pin bought nothing.** Measured: the require line was the *only* reference to Hyprland in this
entire manifest — no `hyprctl`, no Hyprland binary, no `cstream-hyprland` service.

**And its direction was backwards.** The layer's rationale is that *this* pod supplies the parent
Wayland display Hyprland nests into — Hyprland has no headless mode and dies with
`CBackend::create() failed!` without one. A parent requiring its own child states that dependency
the wrong way round.

### One expected consequence, stated rather than hidden

The bed drops from 89 to 88 steps, and `hypr-lock-config` no longer appears. That is **correct**:
with the duplicate gone, `pod-hyprland` is resolved solely from the layer, which still pins
`v2026.242.2008` — the tag from *before* hyprlock got its config. The hyprlock fix therefore reaches
the bed only once `layer-cstream-desktop` repins, which is `layer-cstream-desktop#9`.

That is the intended shape: **one owner for the pin means one place to move it.** Nothing regressed
— the check is absent because the candy providing it is not composed, not because it failed.
