# 2026.242.1926 — fix(R3): use charly's eventually/retry_interval, not a hand-rolled shell retry

## Summary

`cstream-resize-small` hand-rolled retry semantics in shell. charly already provides them as step
modifiers, so this replaces the loop with the existing mechanism.

```diff
-              command: |
-                  for _ in $(seq 20); do
-                      r=$(printf 'resize 640 480\n' | timeout 10 socat - UNIX-CONNECT:...)
-                      case "$r" in
-                          *"OK resize 640x480"*) echo "$r"; exit 0 ;;
-                          *rate-limited*) sleep 0.2 ;;
-                          *) echo "$r"; exit 1 ;;
-                      esac
-                  done
-                  echo "RESIZE-FAIL: still rate-limited after 4s"; exit 1
+              eventually: 15s
+              retry_interval: 1s
+              command: |
+                  printf 'resize 640 480\n' | timeout 10 socat - UNIX-CONNECT:...
```

`eventually:` / `retry_interval:` are the same pair the check skill's
`cross-deployment-probing` reference uses for `cdp:` steps:

```yaml
cdp: {method: open, url: ...}
eventually: 45s
retry_interval: 3s
```

**This was an R3 duplication that I shipped**, and the comment I wrote to justify the loop — *"a
bounded retry is still used rather than a sleep"* — was rationalising a reimplementation instead of
reaching for the seam that already existed. It was found by auditing this session's authored checks
against `/charly-check:check`, which R0 requires loading **before** authoring checks and which I had
not done.

The retry is still necessary and still bounded: the control socket rate-limits **applied** resizes
to 2/s, so a resize arriving too soon after the previous one is refused. The bound keeps a genuinely
dead socket failing rather than hanging.
