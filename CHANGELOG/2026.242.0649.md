# 2026.242.0649 — fix: advance the streamer pin past the merged commit that cannot serve

## Summary

Merged `main` pins `charly-streamer` at **`16faf34`**, which predates the in-process signalling
server. A streamer built from that commit **cannot serve**: webrtcsink's default signaller dials
`ws://127.0.0.1:8443`, and with nothing listening it posts a stream error onto the bus moments
after the pipeline reaches PLAYING. So the candy currently ships a binary that builds its graph,
opens the hardware encoder, prints both success markers — and then dies.

This advances the pin to **`3898e9a`**, `charly-streamer`'s `main` after `#6` merged, which carries
all three commits (delivery half, `verify_openable`, signalling server).

**How the bad pin got in, stated plainly:** auto-merge was armed on the gating PR while follow-up
commits were still being pushed to it, so it merged the moment the checks went green — at a commit
two revisions behind the branch. The lesson is not to arm `--auto` on a PR still under iteration;
recorded here rather than left as an unexplained pin bump.

## Change classification

**Change class:** candy/box-config — one pinned SHA, one candy `version:`. No Go, no schema, no
workflow, single repo.

**Verification gate:** `check-cstream-pod`, and specifically its `cstream-streamer-serves` check —
the one that fails at the old pin.

**Breaking change + rollback:** none in shape; the behavioural consequence is that the streamer's
serving path starts working. Rollback is a plain revert (and restores the broken serving path).

**Producer → consumer order:** satisfied — `3898e9a` is `charly-streamer`'s `main`, merged and
published.

**3. The check that discriminates between the two pins:**

```
PASS  check the streamer SERVES -- the bus loop runs and the sink registers as a producer  [cstream-streamer-serves]  exit=0
```

It runs the shipped binary **without** `--probe`, so it enters the bus loop, and asserts three
things: `CSTREAM-PIPELINE-PLAYING` (the graph negotiated), `registered as [Producer]` (the
in-process signalling server came up **and** the sink registered with it), and exit `124` (still
blocked in the bus loop when the timeout fired — `0`/EOS and `1`/bus-error are both rejected,
because `0` is the one that would otherwise read as success).

At the **old** pin this same check fails with
`Error: pipeline error from GstWebRTCSink:webrtcsink0: GStreamer encountered a general stream
error` — measured, which is what identified the defect in the merged candy in the first place.
