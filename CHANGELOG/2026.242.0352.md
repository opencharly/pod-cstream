# 2026.242.0352 — feat: the cstream transport spine

## Summary

The cstream transport spine: the Wayland parent that **is** the streamer, the browser-facing
gateway, the PAM login stack, and the gates that prove the stack is actually *streaming* rather
than merely started.

The candy composes `layer-gst-wayland-display` (the parent compositor element), `pod-hyprland`
(the nested desktop) and `layer-supervisord`, builds `cstream-gateway` and `cstream-leader` from a
pinned `charly-streamer` commit, declares the two services, stages `/etc/pam.d/cstream`, and
installs four probes.

**Why three of the gates are shaped the way they are.** The obvious checks are not evidence:

- A service check proves a process is up. Measured, charly's own `service:` verb reports **PASS
  for a supervisord program parked in FATAL** (`opencharly/charly#456`), so "the service is
  running" cannot carry a streaming claim on its own.
- A screenshot proves the compositor draws. It says nothing about whether the encoder and
  transport carry those pixels.
- "The frame is not uniform" passes on a wallpaper, so a frozen pipeline serving one static frame
  forever satisfies it.

So `stream-probe` pulls frames **through the pipeline**, maps a real client window, and compares
before against after: a dead, frozen or placeholder pipeline yields identical frames and fails.
`encoder-probe` fails when a VA-capable node is present but hardware H.264 is not actually
producing a stream — the spec's named silent fallback to CPU.

**The PAM stack is deliberately `/etc/pam.d/cstream`, not `login`.** `login` carries
`pam_loginuid` (needs `CAP_AUDIT_CONTROL`) and `pam_securetty` (gates on a tty a streamed session
does not have), so borrowing it makes a **correct** password fail with *"Authentication service
cannot retrieve authentication info"* — an error that names the wrong cause and sends the reader
to inspect the credential.

**What is deliberately NOT here.** The root login **broker**. `pam_unix` delegates to the setuid
helper `unix_chkpwd` whenever euid is not 0, and that helper only verifies the **calling** user's
own account — so cross-user authentication, the broker's entire reason to exist, cannot run, let
alone be gated, in a rootless pod. It lands with `check-cstream-vm`, where a root system service
is real. Two scripts for it were written and then removed from this diff rather than shipped
untested: they also targeted the leader's pre-stdin CLI and put the password back on argv.

**4. The gates DISCRIMINATE — each was made to fail, deliberately, before being trusted.**

- **Streaming.** Tapping the parent pipeline into `fakesink` leaves both services reporting
  running and the login page serving, and `cstream-stream-live` FAILS → the bed FAILS. Restoring
  the sink returns every check to PASS. That two-way control is the whole point: without it the
  gate could be passing on liveness it never actually measured.
- **Login.** The reject leg is not decoration. Run as a uid that cannot verify the account,
  *both* legs fail — so a green reject leg alone would be worthless. The pair is meaningful only
  because the accept leg passes in the same run, against the same stack, on the same account.
- **PAM stack shape.** The first version of `cstream-pam-service` FAILED on a correct file: it
  grepped the whole file for `pam_loginuid|pam_securetty`, and matched this stack's own comment
  explaining why those modules are absent. It now asserts against the module lines only, and was
  re-checked against a deliberately hostile file (`account required pam_securetty.so` → exit 1).
