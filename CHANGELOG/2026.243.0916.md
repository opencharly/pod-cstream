# 2026.243.0916 — feat(WP6): turn desktop audio ON, and gate it on both channels reaching the stream

## Summary

**WP6: desktop audio is on, and gated on both channels actually reaching the stream.**

The two virtual endpoints have existed since `pod-cstream#14` with nothing attached to them. This
attaches them — pin the audio-capable streamer, bridge the runtime-dir split, enable capture, and
assert the result.

Four changes. **Three of them exist because the bed found defects that no local test could have.**

## 1. `PIPEWIRE_RUNTIME_DIR` on the streamer service

PipeWire and the streamer use **different** runtime dirs, and both are correct: this process moves
`XDG_RUNTIME_DIR` to its own Wayland dir, while `pod-pipewire`'s wrapper keeps whatever it inherited
(`/tmp/xdg-runtime` here — note its *default* is `/tmp`, which is what the sibling check's comment
describes and is not what it actually gets). `pipewiresrc` looked where the compositor lives and
failed the pipeline at PLAYING with a bare `Failed to connect`.

A/B in the live pod, one variable:

```
XDG=/tmp/cstream-rt                             → Failed to connect
XDG=/tmp/cstream-rt  PIPEWIRE=/tmp/xdg-runtime  → Execution ended, no error
```

## 2. `CSTREAM_AUDIO=on`

Opt-in since `charly-streamer#10`. Enabled here because this is where the path is now proven.

## 3. The frame probe consumes **both** pads

`webrtcsrc` exposes `video_%u` *and* `audio_%u` as "Sometimes" pads. The bare
`webrtcsrc ! videoconvert` form links only the first, so the new audio track left a dangling pad and
killed the entire flow:

```
streaming stopped, reason not-linked (-1)
```

That reads as a transport fault and is an **unconsumed pad**. Enabling audio broke the **video**
gate — `cstream-frame-through-webrtc` failed while audio itself was fine.

| probe form | result |
|---|---|
| `webrtcsrc ! videoconvert …` | error, 14 frames, death |
| `audio-codecs="<>"` | **not** a fix — transport still built, same error |
| `src.video_0 ! … src.audio_0 ! fakesink` | **1792 frames, no error** |

## 4. The monitor gate asserts both channels

The weak form — *"the monitor has a link"* — **passed** while the stream negotiated a single
`input_MONO` port and PipeWire linked `monitor_FL` only. The right channel was dropped, not mixed;
desktop audio was left-channel-only with every check green. Fixed upstream in `charly-streamer#11`
by pinning `channels=2` on the source caps.

The gate is now written the strong way, so that regression cannot pass, and the half-captured case
is reported distinctly with its cause (a capsfilter placed downstream of `audioconvert` instead of
upstream, where conversion satisfies the caps and the source still takes one channel).

Proven on the live pod — symmetric where it used to be one-sided:

```
before:  cstream-speaker:monitor_FL  |->  cstream-streamer:input_MONO     (monitor_FR: nothing)
after:   cstream-speaker:monitor_FL  |->  cstream-streamer:input_FL
         cstream-speaker:monitor_FR  |->  cstream-streamer:input_FR
```

The port names changing from `input_MONO` to `input_FL`/`input_FR` is the tell that the source
genuinely negotiated two channels rather than downmixing.

place, but nothing writes to it yet.
