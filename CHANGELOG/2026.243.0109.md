## Why virtual endpoints at all

A streamed desktop has no sound card. Applications still need somewhere to play to and something to
record from, and the streamer needs a fixed, **named** place to tap: a null sink's monitor port is
what gets encoded into the outbound audio track, and a virtual source is where the browser's
microphone is injected. The names are load-bearing, not cosmetic — the streamer and the bed both
address these by `node.name`, so renaming one silently detaches the audio path.

`object.linger = true` on both: the streamer attaches at pipeline construction, potentially before
any application has produced a sample, so the endpoints must outlive having no clients.

## Three deliberate choices

1. **`require: pod-pipewire`** rather than installing the packages here. It brings the daemon,
   wireplumber and `pw-cli`, and its service is already **priority 5** — exactly the slot the
   plan's start chain reserves for it (`dbus 2 → pipewire 5 → cstream-broker 8`), so no ordering
   needed inventing.
2. **A drop-in, not a replacement `pipewire.conf`.** Overwriting the shipped config would silently
   discard the distro's own defaults when all that is needed is an extra `context.objects` list.
3. **The gate asserts the NODES, not the file.** A drop-in with a syntax error sits on disk exactly
   like a good one — PipeWire logs the parse failure and carries on with **no endpoints**. A file
   test passes while the audio path does not exist. `pw-cli ls Node` is the state PipeWire actually
   reached, and the failure branch dumps the node names it *did* find so a miss is diagnosable from
   the bed output alone.

This is the same failure shape that has recurred across this stack — a step that reports success
having produced nothing — so the assertion is on the outcome, never on the step.

## What this increment does NOT claim

WP6 is not finished by this PR, and the plan's remaining audio items are untouched:

- **no encode path** — nothing yet routes `cstream-speaker`'s monitor into the outbound track; that
  needs `media/audio.rs` in `charly-streamer`.
- **no microphone transport** — the second PeerConnection that feeds `cstream-mic` is product code,
  not config.
- **no default-sink assignment** — setting `default.configured.audio.sink` via PipeWire metadata is
  a separate step, and `wpctl status` showing cstream as the *default* is deliberately not asserted
  here because nothing sets it yet.

Gating those would be asserting behaviour that does not exist. What is gated is exactly what this
PR builds: the endpoints exist and PipeWire instantiated them.
