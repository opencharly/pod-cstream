# 2026.242.1710 — fix: advance pod-hyprland to the build carrying the wl: tooling

## Summary

Advance `pod-hyprland` to `v2026.242.1704`, the build that ships `wl-clipboard`, `wtype` and
`wlr-randr` beside `grim` — the binaries the `wl:` verb shells out to for clipboard, type/key-combo
and resolution. Without them those verbs fail on `command not found` rather than on anything about
the desktop, which is why none had ever been exercised against this compositor.

## Why this pin moves before the metalayer's

`layer-cstream-desktop` composes **both** this candy and `pod-hyprland`, and this candy pins
`pod-hyprland` independently. Advancing only the metalayer therefore leaves two versions in the
graph — measured, not hypothetical:

```
Warning: candy github.com/opencharly/pod-hyprland resolved to multiple versions;
         using newest 2026.242.1640 (from …@v2026.242.1704),
         ignoring 2026.242.0620 (from …@v2026.242.0634)
```

**Reading those numbers:** charly reports the candy's declared `version:` field and, in parentheses,
the **git tag** it was fetched from — two different numbering spaces, which is why `2026.242.1640`
and `v2026.242.1704` appear together and are not a contradiction. Verified at the tags:

```
pod-hyprland @ v2026.242.0634  ->  candy version: 2026.242.0620   (the "ignoring" side)
pod-hyprland @ v2026.242.1704  ->  candy version: 2026.242.1640   (the "using newest" side)
```

`PickCandyVersion` picks newest project-wide, so resolution would still be *correct* — but by
charly's tie-break rather than by anything the graph declares. Landing this first means the graph
declares one version. (This is the same shape as `opencharly/distro-cachyos#41`, where advancing a
single consumer in a stale tree was measured to take a project from 2 warnings to 6.)

## A finding this tag makes reachable — routed to `opencharly/pod-cstream#11`

Shipping `wlr-randr` makes `wl: resolution` *functional* on a cstream desktop, where it was
previously `command not found`. Measured on this bed, that is harmful:

```
WP4 resize 640 480       ->  streamer 640x480,  compositor 640x480      (coherent)
wl: resolution 1280x720  ->  compositor 1280x720                        (wlr-randr succeeds)
streamer `geometry`      ->  STILL 640x480                              (never told)
```

Encoder and compositor desynced, with no error anywhere — `wlr-randr` is a second writer to a
property the cstream control socket owns.

**This is not parked.** It is filed as **`opencharly/pod-cstream#11`**, which carries the
measurement, the reproduction, and three concrete options (profile-level refusal; making the
streamer track the compositor; bed-level avoidance) with the trade-offs stated so the choice is made
deliberately.

**What this PR does about it now:** the `check-cstream-pod` bed deliberately does **not** gate
`wl: resolution`, and says so inline with this measurement as the reason. The binary still ships
because `wl:` serves other compositors where the verb is correct — refusing to ship it would break
those to avoid a hazard specific to a GWD-driven output.
